# 3. 판정 모델을 공개 모델로 바꾸기

2026-11-11 ~ 11-14 · Jev(jev-1.14.0) → H2O-Lightning-4B · 견준 것: Gemini Decision 1, d1-2B

## 공개 모델도 써 보고 싶었다

Jev로 방식을 정한 뒤에는 공개 모델도 써 보고 싶었다. 가중치가 공개된 모델이면 직접 돌릴 수 있다. 실험을 마음껏 할 수 있고, 키 없이 누구나 열어 볼 수 있는 시연도 만들 수 있다. 프로젝트는 아직 프레임을 어떻게 넣을지 실험하던 중이었다.

옮기는 것 자체는 어렵지 않다. 걱정은 옮기고 나면 그동안 Jev로 얻은 결론(1초마다 4장, 기준값 0.5)이 새 모델에서도 맞는지 알 수 없다는 것이었다.

## 받아 둔 답으로 견주기

Jev에 새로 묻는 대신 이미 받아 둔 것을 썼다. 앞선 실험에서 Jev에 보낸 **같은 프레임, 같은 질문**과 그때 받은 답이 남아 있었다(요청 2,980건: Charades 위치 찾기, 창 열림, 싸움·알림 헛짚음 등 다섯 과제). 새 모델에 똑같은 것을 물어 Jev의 답, 그리고 정답과 견줬다.

- 넣는 모양은 2장에서 정한 A(1초마다 4장 따로)
- 후보: H2O-Lightning-4B(공개 가중치 9.3GB, Apache-2.0), Gemini Decision 1(API), d1-2B(가장 가벼움, 5.7GB)
- 돌린 곳: Colab L4 → Cloud Run → Modal의 RTX PRO 6000

## 나온 것

| 모델 | Charades 한 곳 찾기 (100) | Jev와의 차이 (95% 구간) | 그 밖 |
|---|---|---|---|
| Jev (받아 둔 답) | 89 | — | — |
| **H2O-Lightning-4B** | 86~88 | −0.01 (−0.07 ~ +0.05) | 공개 벤치마크에서도 위쪽 |
| Gemini Decision 1 | 83 | −0.06 (−0.126 ~ +0.011) | 싸움·알림 헛짚음이 0/300으로 가장 적음 |
| d1-2B | 73~76 | 뚜렷이 낮음 | 0.5에서 자르면 맞지 않아 과제마다 기준을 다시 잡아야 함 |

H2O는 Jev와 구별되지 않았다. 같은 종류의 모델(질문과 그림을 읽고 답 자리의 확률을 낸다)이라 질문 틀도 그대로 통했다. d1-2B는 창이 열렸나 같은 쉬운 과제는 됐지만 사람 동작에서 떨어졌다. 까닭은 따로 재지 않았다.

직접 돌리게 되면서 새로 생긴 문제는 속도였다.

| 한 일 | 결과 |
|---|---|
| FP8 양자화 + 한 방향 읽기 + 8건 동시 + 그림 0.5배 | 2,980건에 1,396초 → 379초 (L4 한 대) |
| 그림 0.5배의 값 | 싸움 헛짚음 5 → 11장, Charades AUC 0.858 → 0.841 |
| 서버가 준비되는 시간 | 기본 262~360초 → 계산 그래프 한도와 컴파일 캐시로 153초 |
| GPU 메모리 스냅샷 | 준비 8~11초. 다만 그림 요청이 30%쯤 느려졌고, 고친 뒤에도 "답이 그대로다"까지는 확인하지 못함 |

그림을 절반으로 줄이면 가장 많이 빨라지지만 멀리 있는 적이나 화면 구석의 알림 같은 작은 단서가 사라졌다. 그래서 줄이지 않는 쪽을 기본으로 두었다.

## 정한 것

**H2O-Lightning-4B로 옮겼다.** Jev와의 차이가 가장 작았고, 가중치가 공개라 Modal에서도 Hugging Face Space에서도 같은 판을 돌릴 수 있다는 점이 뒤에서 크게 쓰였다([8장](../08_space_qwen/)). 받아 둔 Jev의 답은 이 뒤에도 새 방식을 견주는 기준으로 계속 썼다.

풀지 못한 것은 서버를 켜는 데 드는 2분 반이다. 웹사이트에서 기다리는 시간의 대부분이 이것으로 남았다.

## 돌아보면: 옮겨서 얻은 것과 잃은 것

숫자로 보면 옮겨서 나아진 것은 없다. 같거나 Jev가 나았다.

| | Jev | H2O-Lightning-4B | |
|---|---|---|---|
| 위치 찾기 (100문항) | 89 | 86~88 | 같음 (차이의 구간이 0을 포함) |
| 손하트, 0.5에서 잘랐을 때 ([1장](../01_jev_feasibility/)) | 정밀도 0.95, 재현율 1.00 | 점수가 높게 나와 헛짚은 구간 8개 | Jev |
| 속도 | 초당 35~44건 | L4에서 초당 약 8건, RTX PRO 6000에서 16.5건 | Jev |
| 기다리는 시간 | 없음 | 서버를 켜는 데 153~360초 | Jev |
| 요청 하나의 값 | 약 $0.0001 (첫 실험 1,470건에 $0.15) | 빌린 GPU에서 약 $0.0001~0.0002 (9,916건에 약 $1.08, 작은 실행은 켜는 시간 때문에 더 비쌈) | 비슷하거나 Jev |

값은 같은 조건으로 잰 것이 아니다. Jev의 것은 한 장씩 넣은 첫 실험이고 H2O의 것은 4장씩 넣은 뒤의 실행이라, 크기만 견줄 수 있다.

얻은 것은 숫자에 잡히지 않는 쪽에 있었다.

- **키 없이 누구나 여는 시연.** 직접 돌릴 수 있는 모델이라 Hugging Face Space에 올릴 수 있었다([8장](../08_space_qwen/))
- **모델을 직접 다루기.** 고르기 질문을 넣고, 같은 모델에게 후보를 다시 확인시키는 일은 모델을 직접 돌렸기에 해 볼 수 있었다([9장](../09_self_recheck/))
- **같은 판을 어디서나.** 같은 가중치를 Modal과 Space에서 돌려 두 곳의 답이 거의 같음을 확인했다(확률의 평균 차이 0.008)

잃은 것은 시간이다. 속도를 올리고 서버 켜는 시간을 줄이는 데 위의 표만큼의 일이 들었고, 8장에서도 모델을 올리는 문제로 다시 시간을 썼다.
