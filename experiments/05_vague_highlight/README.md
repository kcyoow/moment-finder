# 5. "하이라이트만 뽑아줘" — 무엇을 물을지 모를 때

2026-11-14 ~ 11-16 · 판정 모델 H2O-Lightning-4B · 질문을 쓰는 LLM 여럿 · 자료: 마인크래프트 12편(OpenAI VPT), TVSum 50편

## 물을 것이 없다

"다이아 캐는 장면"처럼 딱 집은 요청은 그대로 물으면 된다. 그런데 막상 쓰는 사람은 "하이라이트만 뽑아줘"라고 하기 쉽다. 판정 모델은 예/아니오로만 답하니, 무엇을 예라고 할지를 누군가 정해 줘야 한다. 사람이 영상마다 질문을 쓸 수는 없다. LLM에게 쓰게 하면 되는데, LLM은 영상을 보지 못한다. 무엇을 보여 주고 쓰게 해야 하는지가 이 장의 고민이었다.

## 세 단계로 해 본 것

단계마다 설계와 판정 규칙을 결과보다 먼저 적었다.

1. **구체적 질문과 막연한 질문 견주기.** 마인크래프트 12편(3,600초)에서, 사람이 쓴 구체적 기준(싸움, 피해, 제작, 다이아몬드 등)과 "이 순간이 하이라이트인가" 하나만 묻는 것을 견줬다. 정답은 게임 기록(때린 것, 맞은 것, 만든 것)에서 만든 큰 사건 56곳이다
2. **LLM이 쓴 기준을 사람의 점수와 견주기.** TVSum 50편에는 영상마다 사람 20명이 2초 단위로 매긴 중요도가 있다. LLM에게 제목과 범주만 주고 기준을 쓰게 한 뒤, 판정 모델의 답과 사람 점수의 순위 상관(τ. 1이면 순서가 똑같고 0이면 무관하다)을 쟀다
3. **판정 모델이 먼저 훑고, 그 요약을 보고 쓰기.** 제목조차 없을 때를 위해, 판정 모델이 고정 질문 9개로 영상을 먼저 훑은 요약을 LLM에게 주고 기준을 쓰게 했다. 제목만(T), 제목 + 요약(TP), 요약만(P)을 견줬다

TVSum의 사람 점수는 다시 배포할 수 없어 싣지 않았다. 영상은 CC-BY다.

## 나온 것

| 물음 | 결과 |
|---|---|
| 구체적으로 물으면 나은가 (마인크래프트) | AUC 0.855 대 막연한 질문 0.719 |
| LLM이 쓴 기준이 사람 점수와 맞나 (TVSum) | τ 0.212. 막연한 질문만은 0.166, 사람끼리는 0.177 |
| 요약만 보고 써도 되나 (TVSum) | 요약만 0.212, 제목 0.217, 제목 + 요약 0.224. 요약만 본 기준이 막연한 질문보다는 낫고(+0.046, 구간이 0 위), 제목과의 차이는 가르지 못함 |
| 같은 방식이 마인크래프트에서도 되나 | 안 됨. 요약만 0.515, 게임 설명 0.597~0.662, 막연한 질문 0.720, 사람이 쓴 기준 0.847 |

TVSum에서는 LLM이 쓴 기준이 쓸 만했다. 그런데 같은 방식을 마인크래프트에 가져가니 막연한 질문 하나보다도 나빴다. 두 가지가 눈에 띄었다. 같은 입력으로 기준을 **다시 쓰게만 해도** 결과가 −0.065만큼 흔들렸는데, 이것은 요약을 준 효과(−0.024)보다 컸다. 그리고 요약만 본 LLM은 제작과 인벤토리를 "평온한 장면"의 예로 써서, 제작 순간에 오히려 낮은 점수를 줬다(그 부분의 AUC 0.363).

## 틀린 것은 방법이 아니라 정답이었다

마인크래프트의 결과가 계속 나쁜 까닭을 찾다가, 방법을 고치는 대신 정답을 쪼개 봤다.

| 게임 기록의 큰 사건 56곳 | 수 |
|---|---|
| 도구 제작, 소·양 사냥 | 43 |
| 사람이 하이라이트로 칠 만한 것(다이아몬드, 크리퍼, 위험)에 닿는 것 | 13 |

게임 기록은 "눈에 띄는 일"이지 "보고 싶은 일"이 아니었다. LLM은 게임 설명을 보고 싸움 쪽으로 기준을 썼는데, 정답의 대부분은 제작이었으니 점수가 나쁠 수밖에 없었다. 사람이 말한 하이라이트에 맞춘 표시로 다시 재니 순서가 뒤집혔다(LLM이 쓴 질문 0.796 대 사람이 쓴 기준 0.660). 이 표시는 결과를 본 뒤에 만든 것이라 진단으로만 쓰고 성적으로는 적지 않는다.

TVSum에서 사람끼리의 일치(0.177)가 LLM의 기준(0.212)보다 낮다는 것도 같은 이야기다. "하이라이트"는 사람마다 다르고, 막연한 요청에는 잴 정답이 없다. 며칠을 방법 쪽에서 헤맨 뒤에야 재는 자를 의심했다.

## 다음으로

두 가지를 가져갔다. 구체적인 질문이 낫다는 것, 그리고 LLM이 요청만 보고도 쓸 만한 질문을 쓴다는 것이다. 이것이 [6장](../06_pipeline_site/)의 "질문 쓰기" 단계가 됐다.

막연한 요청은 LLM이 혼자 정하게 두지 않기로 했다. LLM이 어떻게 이해했는지를 보여 주고 사용자가 맞다고 해야 진행한다. [8장](../08_space_qwen/)과 [9장](../09_self_recheck/)의 "이렇게 찾을까요?"가 여기서 나왔다.
