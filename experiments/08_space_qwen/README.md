# 8. 바깥 API 없이: 공개 모델 둘을 ZeroGPU Space에 올리기

2026-11-17 ~ 11-23 · 판정 모델 H2O-Lightning-4B · 중간 LLM Qwen3.8-27B-FP8 · 코드 [`space/`](../../space/)

## 내 컴퓨터에서만 도는 것으로는 보여 줄 수 없다

6장의 웹사이트는 내 컴퓨터에서만 돌고, Modal 계정과 Gemini 키가 있어야 한다. 다른 사람이 열어 볼 수가 없다. 누구나 주소 하나로 써 볼 수 있게 하려면 무료 GPU(Hugging Face ZeroGPU)에서 **공개 모델만으로** 같은 흐름이 돌아야 했다. 판정 모델은 이미 공개 모델이다. 문제는 질문을 쓰는 LLM까지 공개 모델로 바꿔 48GB GPU 하나에 함께 올릴 수 있느냐였다.

## 판정 모델을 옮기기

Modal에서는 vLLM 서버를 띄워 물었지만 ZeroGPU는 서버를 띄워 둘 수 없다. GPU가 요청이 올 때만 잠깐 붙는다. 그래서 transformers로 직접 계산하게 바꿨다. 모델이 배포하는 프롬프트 코드를 그대로 불러 같은 글을 만들고, 답 자리의 확률을 읽는다. 같은 영상으로 Modal의 답과 견주니 확률의 평균 차이가 0.008이었다.

100초짜리 화면 녹화(지갑, 열쇠, 선글라스가 차례로 나옴)로 시험하니 물체가 일부만 나왔다. 원인은 셋이었다. 막연한 질문 하나로만 점수를 매겼고, 클립 길이를 영상의 15%로 묶는 한도가 있었고, 앞뒤 평균이 1초짜리 장면을 지웠다. 요약용 규칙을 찾기에 그대로 쓴 탓이다. 점수가 높은 봉우리부터 최대 5개를 잡고 길이 한도를 없앤 "찾기" 규칙을 따로 만들자 세 물체가 모두 나왔다.

## Qwen3.8-27B를 48GB에 올리기

가장 오래 걸린 부분이다. 27B 모델을 48GB에 올리려면 FP8(8비트) 그대로 써야 한다. 처음에는 FP8 모델이 96GB GPU에만 올라간다고 잘못 알고 4비트로 가려 했다. 공개된 다른 Space의 코드와 라이브러리 소스를 직접 읽고서야 48GB에도 그대로 올라간다는 것을 알았다. 설명 글만 보고 "안 된다"고 판단했던 것이 틀렸다.

올린 뒤에도 문제가 이어졌다.

| 부딪힌 것 | 원인 | 고친 것 |
|---|---|---|
| 답이 망가짐 | 라이브러리가 "FP8로 바꾸지 않을 층" 목록을 앞부분 일치로 봐서, `mlp.gate` 항목이 `mlp.gate_proj` 65개 층까지 건너뛰게 했다 | 그 항목을 목록에서 뺐다 |
| 첫 토큰까지 37~66초 | FP8 행렬곱 커널이 모양마다 설정 12가지를 컴파일해 재 보고 고른다 | 설정을 하나로 묶었다 → 약 10초 |
| 설정을 묶자 메모리 오류 | 고른 설정이 GPU의 블록당 공유 메모리 한도를 넘음 | 단계 수를 3에서 2로 |
| 질문 쓰기 뒤의 판정이 거절됨 | ZeroGPU는 요청마다 받은 토큰으로 GPU를 잡는데, 그 토큰이 한두 분이면 만료된다 | GPU 호출을 요청 하나에 한 번만 하고, 화면이 단계를 이어 부른다 |

| 잰 것 | 결과 |
|---|---|
| 판정 속도 | 한 번 읽기 약 0.16~0.18초. 60초 영상에 질문 4개면 GPU 약 45초 |
| Qwen의 쓰기 속도 | 첫 토큰까지 약 10초, 초당 약 8토큰, GPU 메모리 최고 약 44GB |
| 화면 녹화에서 물체 찾기 (Qwen이 쓴 질문 3개) | 클립 4개가 모두 맞음(지갑, 선글라스, 열쇠 둘) |

두 모델이 같은 구조(Qwen3.5)라서 커널 문제를 한 번 고치니 판정 모델도 함께 빨라졌다.

## 대화로 되묻기

느린 것은 쓰기다. 판정 모델은 답 자리 하나만 읽으니 빠르지만, Qwen은 글을 한 토큰씩 써야 해서 한 번 쓰는 데 GPU 1~2분이 든다. 무료 한도가 하루 몇 분이니 Qwen을 여러 번 부를 수가 없다. 설계가 "Qwen을 한 번만 부른다"는 쪽으로 갔다. 한 번의 답에 1초마다 물을 질문 3개와 다시 확인용 정의를 함께 쓰게 했다.

그 한 번을 어디에 쓸지는 5장과 7장에서 정해져 있었다. 막연한 요청을 LLM이 혼자 정하면 빗나간다. 그래서 Qwen이 "이렇게 찾을까요?" 하고 **찾을 장면과 헷갈려서 빼려는 장면**을 먼저 보여 주고, 사용자가 맞다고 하거나 고쳐 말한 뒤에 판정을 시작한다.

이 단계가 왜 필요한지는 최종 시험에서 바로 드러났다. Qwen은 검색을 하지 못하고 아는 것만으로 쓴다. "마크 영상인데 싸우는 장면"이라는 요청에서 "마크"를 마인크래프트가 아니라 마크라는 사람으로 읽었다([9장](../09_self_recheck/)). Gemini는 모르는 것을 검색해 확인했다. Qwen의 이 빈틈은 되묻기 화면에서 사용자가 메워야 한다.

## 다음으로

질문 쓰기는 공개 모델로 바뀌었다. 남은 바깥 API는 다시 확인 단계의 Gemini 하나다 → [9장](../09_self_recheck/)

풀지 못한 것도 있다. 방문자는 자기 계정의 하루 GPU 한도를 쓴다(로그인하지 않으면 2분, 무료 계정 5분). 한 번 돌리는 데 2~6분이 들어 끝까지 못 돌 수 있다. 그래서 화면에 미리 돌려 둔 예시를 넣었다.
